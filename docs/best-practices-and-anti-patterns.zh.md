# 最佳实践与反模式

整条应用层 LLM 技术栈的该做/不该做，集中在一处，从各个 notebook 里采撷而来，按章节
组织。两个用途：

- **面试前复习。** 「搭这个系统你会注意什么？」是真实的系统设计 / 客户场景面试题。
  这就是标准答案。
- **结业项目前的清单。** 在你交付简历项目（第 12 节）之前，照这张表走一遍，确认每一
  行你都站在 ✅ 这一边。

反模式故意紧挨着它所违反的那条实践：错误是记住规则最快的方式。每一节都链到它被讲授的
地方。

---

## 00：Setup 与「非确定性」心态

| ✅ 该做 | ❌ 反模式 |
|---|---|
| 把模型当作**概率性**的存在；同样的输入可能给出不同的输出 | 以为「跑通过一次」就等于能跑；肉眼看一眼就上线 |
| key 放在 Colab Secrets / 环境变量里 | 把 API key 直接粘到 cell 里（会被提交或被截图） |
| 调用套上花费护栏；清楚每个 token 的成本 | 拿付费 key 跑无界循环，然后从账单里才知道后果 |
| 迭代期间默认用最大的模型；批量处理时降到小模型 | 为了「保险」所有事都用最大的模型 |

## 01：Model APIs

| ✅ 该做 | ❌ 反模式 |
|---|---|
| 用**工具/函数调用**来强制结构化输出（把 schema 当代码） | 「直接要 JSON」然后祈祷；永远用正则去解析散文 |
| 在代码里校验业务规则，把错误回喂给模型重试 | 把 `strict:true`（各家支持不齐）当作唯一的护栏 |
| 在工具**描述**里写清楚*什么时候*该调用；它们就是 prompt | 描述含糊（「做数学」）；模型该触发时不触发、不该触发时乱触发 |
| 为了体验做 streaming；始终捕获最后那个 usage/`x_groq.usage` chunk | 丢掉尾部的 chunk，也就丢掉了计费记录 |
| 给输出留出余量；给上下文的四条线做预算 | 因为「塞得下」就填满上下文窗口；为成本蠕变买单 |

## 02 / 04：Evals（主线）

| ✅ 该做 | ❌ 反模式 |
|---|---|
| **先度量，再调优**——黄金集 + 一个数字，卡住每一次改动 | 靠感觉和一次侥幸的输出调 prompt/分块大小/模型 |
| 只 pin 机器可校验的字段；覆盖你*害怕*的那些情况 | 黄金集里只有顺利路径的 case；用脆弱的精确字符串匹配 |
| 用一个*不同的、更便宜的*模型来评判；把分数锚定到评分标准上 | 让模型给自己的输出打分；没有锚点的 1–5 分（最后什么都是 3.5） |
| 判分时先推理再给分；用人工标注来做校准 | 先给分（事后找理由）；把一个没校准过的 judge 直接上线 |
| 两类门禁：预算门禁（有噪声的聚合指标）+ 零容忍门禁（绝不能上线） | 只有一个全局阈值；因为单个 case 抖动就卡住合并 |
| 每一次生产故障都变成黄金集里的一个新 case | 修完 bug 却不记录它；下个月又踩一次 |

## 03：RAG

| ✅ 该做 | ❌ 反模式 |
|---|---|
| 记住 RAG = *先检索再生成*；检索那一步可以是任何方法 | 把「RAG」和「embedding/向量数据库」混为一谈；关键词/SQL/API 也算 |
| 答案错的时候，**先检查检索** | 怪模型，然后开始重写 prompt |
| 分块之前先清洗语料；垃圾进 → 垃圾 embedding | 带着页眉页脚/样板文字去 embed 原始文档 |
| 语料本身有结构时，优先用结构感知的分块 | 在还没法度量检索之前，就迷信分块大小的调优 |
| 只有 eval 证明混合检索/rerank 值回成本时才加上 | 因为每一级检索「听起来都合理」就层层叠加 |
| 语料覆盖不了问题时，让模型拒答 | 任由它凭预训练知识自信作答、不给引用 |

## 05：Agents

| ✅ 该做 | ❌ 反模式 |
|---|---|
| 步骤事先已知时，直接用 **pipeline** | 把每个任务都包进一个自主 agent（一件披着风衣的 pipeline） |
| 给每个循环设界：max_turns、成本、墙钟时间、循环检测 | 拿付费 key 跑无界循环；「它一般会自己停」 |
| 对破坏性/不可逆的操作加人工闸门；默认拒绝 | 让 agent 不经确认就删除/发送/付款 |
| 每个工具最小权限；范围卡紧，按*用户*的权限来执行 | 给一个 `run_sql`/`run_shell` 万能工具，模型想指哪就指哪 |
| 给**轨迹**（工具调用路径）打分，而不只看最终答案 | 接受一个看着对、但由离谱且昂贵的路径得来的答案 |
| 失败时大声报错，带上状态和部分 trace | 悄悄截断，把半成品当完成品返回 |
| 明白 MCP 映射的就是原生工具循环；当集成收益足够时才采用 | 还没搞懂它包住的那个循环，就先去够框架 |
| 把*偶尔用到、但很细*的经验打包成一个 **skill**（按需加载）；把一直相关的几行留在 prompt 里 | 把每本操作手册都塞进 system prompt，每一轮都为全部内容付费 |
| 把 skill 的 **`description`** 写给模型看：它做什么，*以及什么时候用它* | 描述写得含糊，然后纳闷 skill 为什么从不触发 |
| 把脆弱逻辑推到一个随包提供、已验证的 **script** 里（只有它的输出消耗上下文） | 让模型每轮都在上下文里重新推导同一套脆弱的流程 |
| 把已安装的 skill 当作可信代码；第三方的一律先审（见 07） | 装一个公开 skill 就默认它的正文/脚本是安全的 |
| 把上下文窗口当作每一轮都要重建的预算；长对话要压缩（保留任务 + 最近几轮 + 已承诺事项） | 以为模型「记得」；让记录无界增长，直到撑爆窗口和账单 |
| 每个工具结果重新进上下文之前先整形：限制大小（头+尾）、让错误可操作 | 把原始大块内容/裸堆栈直接喂回去，每一轮都重发一遍 |
| 在代码里校验输出，失败就有界地循环重试；在 harness 里算出 ground truth | 相信模型自己说的「done」；第一个看着对的答案就交付 |
| 结果不稳定时，先修 harness（上下文、结果、校验、边界） | 在脚手架还没理顺之前就去换更大的模型或上微调 |

## 06：适配模型

| ✅ 该做 | ❌ 反模式 |
|---|---|
| 按顺序试杠杆：**prompt → RAG → fine-tune**，只有 eval 失败才往前一步 | 因为觉得「这才像真的做 ML」就先上 fine-tune |
| 为风格/格式/窄任务成本而 fine-tune（调行为，不是灌知识） | 想靠 fine-tune 加知识（那是 RAG 的活；知识会过时、无法引用） |
| 默认用 **LoRA** 而不是全量微调：便宜、单卡、adapter 可热插拔、遗忘更少 | 默认做全量微调；把它留给剧变场景（新语言、深度推理） |
| 一个冻结基座 + 热插拔 adapter 来服务多个变体 | 每个任务单独起一个完整的模型，为闲置的 GPU 付费 |
| 用同一套 eval harness 证明 fine-tune 胜过 prompt+RAG | 因为*感觉*更好就交付一个 fine-tune；没有任何前后对比数字 |
| 除非需要完全掌控，否则优先用托管 fine-tuning API | 为一个只会做两次的决定，去搭一整套 GPU 训练栈 |

## 07：Security

| ✅ 该做 | ❌ 反模式 |
|---|---|
| 把**所有**模型能看到的文本都当作攻击者可控制的（含 RAG/工具） | 信任检索到的文档或工具输出是安全的 |
| 模型**输出**进入任何去处（数据库、shell、HTML、发送）之前先校验/白名单 | 把模型原始输出直接喂进有后果的动作 |
| 最小权限 + 人在回路；假设模型*一定会*被劫持 | 把 system prompt 当作安全边界（它会泄露） |
| 让密钥/PII 远离上下文；记录日志前先脱敏 | 把 key/其他用户的数据塞进 prompt「以防万一」 |
| 纵深防御，让任何单点失败都不至于酿成灾难 | 相信某个「prompt 注入修复」就能让你安全 |

## 08：Operations

| ✅ 该做 | ❌ 反模式 |
|---|---|
| 追踪每一次调用（输入/输出/token/延迟/状态）；抽样保存完整 payload | 什么都不记，或者记录原始的 prompt（一次无声的 PII 泄漏） |
| 同时看 p50 **和** p95/p99；对变化量告警，而不是对绝对值 | 只看均值；漏掉用户真实感受到的长尾 |
| 对瞬时错误用带退避+抖动的重试；对 4xx 快速失败 | 什么都重试，或者什么都不重试；重试同步化引发惊群 |
| 超时 + 降级模型 + 优雅降级；上报一个 `degraded` 指标 | 让一次卡住的调用阻塞用户；返回裸的 500/异常 |
| 把校验输出当作可靠性检查（200 ≠ 可用） | 以为 HTTP 200 就意味着响应可解析/可用 |
| 把生产故障回灌进 eval 集（飞轮） | 把可观测性当作只看一次的仪表盘 |

## 09：客户手艺（FDE）

| ✅ 该做 | ❌ 反模式 |
|---|---|
| 动手之前，先把一句含糊的需求变成范围清晰、*可数字化*的成功指标 | 还不知道成功是什么意思，就开始搭「给 X 用的 AI」 |
| 问清楚当前的工作流，以及它在哪里断掉 | 问「你想让 AI 做什么？」，然后接受那个云里雾里的回答 |
| 让「做错的代价」决定护栏/eval 的深度 | 不管风险高低都用同一套架构 |
| 交付最小可用的那一小片；明确说出什么不在范围内 | 想一口吃成胖子；范围无界地膨胀 |
| 在 demo 里，把「做不到什么」说清楚 | 过度承诺；那个惊艳但脆弱、一上生产就死的 demo |

## 最重要的五条

如果其他什么都不记：

1. **去度量，别无凭肉眼**——黄金集 + 一个数字，才让其他一切改动变得安全。
2. **先查检索再 debug**——烂的 RAG 答案几乎总是检索的问题。
3. **先 pipeline 再 agent**——自主性是昂贵时的最后手段，不是默认选项。
4. **模型输出是不可信输入**——进入任何有后果的去处之前先校验。
5. **Prompt → RAG → fine-tune**——只有更便宜的杠杆没过 eval 时才往前一步。
