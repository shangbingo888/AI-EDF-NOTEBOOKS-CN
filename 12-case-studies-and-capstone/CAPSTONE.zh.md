# 结业项目：那个真正部署上线的项目

notebook 教你技能；这个项目才是写进简历的东西。
它刻意**不是**一个 notebook：在一个筛选生产判断力的面试环节里，notebook 项目会传递出
「周末玩家」的信号。把它做成一个真实、已部署的仓库，让你能给面试官递上一个链接。

**先看一遍做好的实例：**[案例研究 A](01-customer-support-assistant.zh.ipynb) 从一个含糊的
需求出发，走完一个项目（一个客服助手）的全程，一直到部署上线、再**在生产中 debug**，
每个阶段都有可运行的代码。它就是你即将动手搭的那个东西的形状；动手之前先读（并跑）它。

## 不可妥协的要求

- **真实数据**——一份乱糟糟的语料或工作流，而不是玩具数据集。
- **一个不是你自己的真实用户**——朋友的生意、你所在的团队、一个开放社区。面试会追问
  你是怎样把他的模糊需求翻译成一个系统的（第 11 节）。
- **一个 serving 组件**——一个已部署、可给链接的 API 或应用，你能推理它在负载下的表现
  （第 09–10 节）。
- **一套 eval 方法论**——一份写成文、随时间追踪的 eval 报告；「它能跑」不算
  （第 02、04、08 节）。
- **一份写作总结**——用户的问题、系统、eval 结果、你下一步会做什么。你应当经得起围绕
  它的 15 分钟拷问式追问。

## 用现代技术栈，别重复造轮子

教学 notebook 是*刻意*不用框架的：你从原生零件出发搭出 agent 循环、RAG 和 evals，好
理解每个库到底在做什么。**结业项目正是你把这个反过来做的地方**——把真实的技术栈组装
起来，并准备好为每个工具解释*它做什么、你为什么选它*。那条「我先手写一遍，再去够框架」
的弧线，本身就是个很有力的面试答案。

一套主流、简历上看得懂的技术栈（按你项目的需要挑，不必全上）：

| 层 | 伸手去够 | 讲授于 |
|---|---|---|
| **RAG / 编排** | LangChain、LlamaIndex 或 LangGraph | 03（+ bridge）、05 |
| **Serving / 推理** | vLLM 或 TGI（自托管）；先用托管 API 起步 | 09/01 |
| **推理性能** | 连续批处理、量化、KV-cache 容量估算 | 09/02 |
| **Fine-tuning（如果值回代价）** | 用 PEFT 做 LoRA / QLoRA | 06 |
| **实验追踪与模型注册表** | MLflow：追踪每一次 eval run，注册线上模型 | 08/03 |
| **可观测性** | tracing、安全日志、成本/延迟指标 | 08/01 |

> 你**不是**在做算法方向；没人指望你发明新模型。这里招人的信号是
> **AI 分布式系统 / 应用工程**：把一套现代技术栈接进一个已部署、已评测、可运维的系统，
> 并有意识地做成本/延迟/质量的取舍。

## 几个强有力的形态

1. **在一个真实的乱语料上做 RAG**——通过 API（vLLM 或某个托管 endpoint）对外提供，
   配一份 MLflow 追踪的 eval 报告，展示你度量了什么、又因它改了什么。
2. **一个把真实多步工作流自动化的 agent**——带护栏、带成本预算，用 LangGraph 编排，
   端到端可追踪。
3. **你现在工作里的一个内部 AI 工具**——采用率数字比架构图更有说服力。

## 展示系统思维（第 09–10 节）

这一层把「调过一个 API」和「掌管 serving 层」区分开。在你的总结里放一小节
**系统设计**：

- **规模估算**——10/01 里的草稿纸推算：预期 QPS、每请求 token 数，因此需要多少 GPU
  （或托管 endpoint 的成本），以及涨到 10 倍时它在哪里先垮。
- **性能**——你真的拉过的那一根杠杆，以及它实测的效果（批处理吞吐、量化带来的
  质量/延迟取舍、prompt 缓存），绑到一个数字上。
- **可靠性与成本**——重试/超时/降级（08/02），以及月成本，和你会去拧哪个旋钮来砍它。

面试官会追着数字问。「峰值 QPS ≈40，70% 利用率下约 2 张 GPU，约 $3k/月，量化一下砍
一半」是及格答案；「部署在云上」不是。

## 模拟一个团队：角色、Agile/Scrum 和简历故事

这段经历在你简历上应当读起来像**一份实习级别的项目**，也就意味着它需要一个*工作流程*
的故事，而不只是一个成果物。面试官会问「你的角色是什么？团队怎么协作？你怎么应对需求
变化？」所以，去搭（或跟你的导师角色扮演）一套真实的交付流程，并搞清楚你在其中坐在
哪个位置。

**按 sprint 来跑。** 两周一个 sprint，配一个 backlog、sprint planning、standup 节奏和
一次 retro。用 ticket（GitHub Issues/Projects 就行）追踪工作。就算单干，也用 sprint 的
方式来讲它；面试里真正讨论的就是这种工作方式。

**搞清楚各个角色，哪怕你一人兼了好几个。** 在一个真实团队里，这个项目会分摊到：

| 角色 | 负责 | 在本项目里 |
|---|---|---|
| **Product Manager** | 用户问题、优先级、验收标准 | 范围界定文档（第 11 节）；「好」意味着什么 |
| **Tech Lead / EM** | 架构、任务拆解、评审 | 系统设计（10）；把工作拆成 ticket |
| **AI/ML Engineer** | prompt、RAG、agent、fine-tune、evals | 01–06 的大部分；eval harness |
| **Platform / MLOps** | serving、部署、CI、追踪、注册表 | 08–09；MLflow、部署 |
| **SRE / On-call** | 可靠性、监控、事故响应 | 08/02；runbook |
| **QA / Eval owner** | 黄金集、回归门禁、签核 | 02、04；「能不能安全上线？」 |

挑一个你打算在简历上**认领**的角色（通常是 AI/ML Engineer，或者一个混合的 AI 系统
角色），把它吃透，并且能讲清楚你怎样把工作交接给别人、又怎样依赖别人：这正是那道
协作题要考的东西。

> **导师角色扮演（推荐）。** 让你的导师扮演 PM/利益相关方：丢给你一句含糊的需求、
> 在 sprint 中途改需求、对你的 demo 挑刺，并在一次模拟评审里问「为什么是这个架构？」
> 排练那些*流程*问题，跟排练技术问题一样重要；多数候选人能描述系统，却在「团队当时
> 是怎么拍板的？」上卡壳。

**写进简历时，用流程 + 影响的方式**，比如：
*「为 [真实用户] 在 [真实语料] 上搭建并部署了一个 RAG 助手；以两周 sprint 的节奏掌管
AI/eval 层，在 vLLM 上服务，配一道 MLflow 追踪的 eval 门禁；通过检索调优与量化把回答
成本砍掉 40%，并用一个 50 个 case 的黄金集验证。」*

## 交付之前

过一遍[最佳实践与反模式速查表](../docs/best-practices-and-anti-patterns.zh.md)：
整条技术栈的该做/不该做都集中在一处。它同时也是「搭这个系统你会注意什么？」这道面试题
的标准答案。在你宣布完工之前，确认你的项目在每一行都站在 ✅ 这一边。

## 面试就绪自检

在你宣布结业项目完工之前，确认下面每一条你都能不假思索地回答。它们是整个仓库一直在为你
准备的面试轮次：

- **范围界定**——「你是怎样把用户含糊的需求变成这个系统的？」（11）
- **技术深挖**——「带我过一遍检索 / agent 循环 / 你的 evals」，并讲清每个选择*为什么*
  （03–06）
- **系统设计**——「你会怎样把它扩展到 10 万用户？」（09–10）
- **运维**——「你怎么知道它在生产里还在正常工作？」（08）
- **安全**——「用户粘一段 prompt 注入进来会怎样？」（07）
- **协作 / 流程**——「你的角色是什么，团队是怎么把它交付出去的？」（本页）

哪个答案还虚，就回到那一节的 notebook 去补。
